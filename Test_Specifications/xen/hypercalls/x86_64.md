# x86_64 Xen hypercall wrappers: example specification

> **Example only.** This document demonstrates the intended structure for
> source-derived requirements and tests in the hypercalls group. It covers the
> calling mechanism and three wrappers; the remaining wrappers are listed as a
> coverage gap. It is not an approved safety artifact.

## Source scope

- `plat/xen/include/xen-x86/hypercall.h`: includes `hypercall64.h` under
  `__X86_64__` (lines 37–39).
- `plat/xen/include/xen-x86/hypercall64.h`: the `_hypercallN` macros and the
  `static inline` wrappers.
- `plat/xen/x86/entry64.S`: defines `hypercall_page` and advertises it to Xen.
- `drivers/xen/xenheaders/include/xen/xen.h`: `__HYPERVISOR_*` numbers and the
  compatibility remapping that depends on `__XEN_INTERFACE_VERSION__`.
- `plat/xen/Makefile.uk`: sets `__XEN_INTERFACE_VERSION__` to `0x00030205`
  for assembly, C, and C++ (lines 1 and 22–24).

## Source observations

- Each `_hypercallN` macro emits one `call` to
  `hypercall_page + (__HYPERVISOR_<name> * 32)`, takes the result from `rax`,
  and casts it to the wrapper's return type.
- Arguments are bound to registers in this order: `rdi`, `rsi`, `rdx`, then
  `r10` and `r8` (moved explicitly in `_hypercall4` and `_hypercall5`).
- Every macro lists `"memory"` as a clobber.
- `hypercall_page` is a global label in `entry64.S` that reserves one page of
  zero bytes directly after the page-aligned `_libxenplat_shared_info` page.
  Under `XEN_PARAVIRT`, an ELF note of type `XEN_ELFNOTE_HYPERCALL_PAGE` names it.
- With interface version `0x00030205`, none of the compatibility remappings in
  `xen.h` (lines 138–155) apply to the wrappers in this document.

## Requirements

### REQ-HCALL-X86-001: call target

When a wrapper built on a `_hypercallN` macro is called, the implementation
shall execute a `call` to the address `hypercall_page + __HYPERVISOR_<name> * 32`,
where `<name>` is the macro's `name` argument.

**Source trace:** `plat/xen/include/xen-x86/hypercall64.h:_hypercall0` to `_hypercall5` (lines 57–130; the `call` string at lines 61, 72, 83, 94, 108, 122).

### REQ-HCALL-X86-002: argument registers

When a wrapper built on `_hypercallN` is called, the implementation shall
place arguments 1 to 5, cast to `long`, in `rdi`, `rsi`, `rdx`, `r10`, and
`r8` respectively, for as many arguments as N.

**Source trace:** `plat/xen/include/xen-x86/hypercall64.h:_hypercall1` (lines 68–77), `_hypercall2` (79–88), `_hypercall3` (90–101), `_hypercall4` (103–115), `_hypercall5` (117–130).

### REQ-HCALL-X86-003: result and compiler ordering

When the call returns, the implementation shall return the value in `rax`
cast to the wrapper's declared type, and each macro's `asm` statement shall
declare a `"memory"` clobber.

**Source trace:** `plat/xen/include/xen-x86/hypercall64.h:_hypercall0` to `_hypercall5` (`"=a" (__res)` outputs; `"memory"` clobbers at lines 64, 75, 86, 99, 113, 128).

### REQ-HCALL-X86-004: wrapper table

Each wrapper in Table 1 shall invoke the macro, hypercall name, and argument
order listed for it.

**Table 1**

| Wrapper | Lines | Macro | Hypercall name (number at `0x00030205`) | Arguments in order | Return type |
| --- | --- | --- | --- | --- | --- |

| `HYPERVISOR_set_timer_op` | 199–204 | `_hypercall1` | `set_timer_op` (15) | `timeout` | `long` |

### REQ-HCALL-X86-005: hypercall page reservation

The implementation shall define a global symbol `hypercall_page` that labels
`__PAGE_SIZE` zero bytes placed directly after the page-aligned
`_libxenplat_shared_info` page, and, when `XEN_PARAVIRT` is defined, shall
emit an ELF note of type `XEN_ELFNOTE_HYPERCALL_PAGE` whose value is
`hypercall_page`.

**Source trace:** `plat/xen/x86/entry64.S` (`.globl` at line 178, `.align __PAGE_SIZE` at line 181, `_libxenplat_shared_info` at lines 182–183, `hypercall_page` at lines 185–186, ELF note at line 52 inside `#ifdef XEN_PARAVIRT`).

## Tests

### TEST-HCALL-X86-001: generated code for the table wrappers

**Traces to:** REQ-HCALL-X86-001, REQ-HCALL-X86-002, REQ-HCALL-X86-003, REQ-HCALL-X86-004

**Method:** compile and disassemble

**Status:** Proposed, not run

**Preconditions:** An x86_64 cross or native compiler, `objdump`, the Xen
include paths and defines from `plat/xen/Makefile.uk` (including
`-D__XEN_INTERFACE_VERSION__=0x00030205` and `-DXEN_PARAVIRT`), and a test
unit with an external `hypercall_page` symbol.

**Steps:**

1. Write one non-inline test function per Table 1 wrapper that calls it with
   distinctive constants: `HYPERVISOR_sched_op(0x11, (void *)0x2222)`,
   `HYPERVISOR_set_timer_op(0x3333)`, and
   `HYPERVISOR_set_segment_base(0x44, 0x5555)`.
2. Compile at `-O2` and disassemble with `objdump -dr`.

**Expected result:** For each function, the constants are loaded into the
registers named in REQ-HCALL-X86-002 in argument order; there is exactly one
`call`, and its target resolves to `hypercall_page` plus 29×32 (`0x3a0`),
15×32 (`0x1e0`), and 25×32 (`0x320`) respectively (a PC-relative relocation
shows an addend 4 lower, for example `hypercall_page+0x39c`); the function
returns the value left in `rax` (`eax` where the return type is `int`).

### TEST-HCALL-X86-002: memory clobber and macro coverage

**Traces to:** REQ-HCALL-X86-001, REQ-HCALL-X86-002, REQ-HCALL-X86-003

**Method:** source inspection

**Status:** Proposed, not run

**Preconditions:** None.

**Steps:**

1. Read each of the six `_hypercallN` macros.
2. For each, record the `call` string, the output and input constraints, any
   explicit `movq` into `r10` or `r8`, and the clobber list.

**Expected result:** All six macros use the same `call` string; register
bindings match REQ-HCALL-X86-002; every clobber list contains `"memory"`.

### TEST-HCALL-X86-003: hypercall page in the image

**Traces to:** REQ-HCALL-X86-005

**Method:** configured build plus image inspection

**Status:** Proposed, not run

**Preconditions:** An x86_64 Xen configuration with `CONFIG_XEN_HVMLITE`
not set, a built image, `nm`, and `readelf`.

**Steps:**

1. Run `nm` on the debug image and read the addresses of
   `_libxenplat_shared_info` and `hypercall_page`.
2. Run `readelf -n` on the image and find the note with owner `Xen` and type
   `XEN_ELFNOTE_HYPERCALL_PAGE` (value 2, from
   `drivers/xen/xenheaders/include/xen/elfnote.h` line 48).

**Expected result:** `_libxenplat_shared_info` is page aligned;
`hypercall_page` equals that address plus `__PAGE_SIZE`; the note's value
equals the address of `hypercall_page`.

## Assumptions

- Xen fills `hypercall_page` with one 32-byte stub per hypercall number when it
  loads the guest, in response to the ELF note. Nothing in the guest source
  establishes this.
- Xen implements each hypercall as its public headers describe.

## Open questions

- None for the covered wrappers.

## Coverage gaps

- The other wrappers in `hypercall64.h` (for example `HYPERVISOR_mmu_update`,
  `HYPERVISOR_event_channel_op`, `HYPERVISOR_vcpu_op`) are not yet in Table 1.
- `HYPERVISOR_shutdown` and `HYPERVISOR_suspend` build a structure before the
  call and need their own requirements.
- `HYPERVISOR_xsm_op` in `hypercall.h` (lines 46–49).
- `hypercall32.h` is not built: x86-32 cannot be selected with `PLAT_XEN`.
